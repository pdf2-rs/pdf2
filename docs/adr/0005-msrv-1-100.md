# ADR 0005 — The MSRV is 1.100, and edition 2024

- **Status**: accepted, 2026-11-17
- **Supersedes**: the *floor* in [ADR 0004](0004-image-decoders-and-the-msrv.md)
  (its decoder decision stands; only the "1.87" it was made against is gone)
- **See also**: [`docs/MSRV.md`](../MSRV.md) — what 1.88–1.100 brought, per release

## Context

ADR 0004 chose `zune-jpeg` for DCT because it was the only decoder that cleared the
then-floor of **1.87**, and deferred JPEG 2000 and JBIG2 to "an MSRV move" because
`hayro-jpeg2000` 0.5.0, `hayro-jbig2` 0.4.0 and `hayro-ccitt` 0.5.0 all declare
`rust-version = "1.92"`. It also wrote down what that move would cost: a decision
about *who can build this crate*, not a technical problem.

Two things changed. **Rust 1.100.0 shipped 2026-11-12** — the floor we can have is
now well past 1.92 — and edition 2024 has been stable since 1.85, so there is no
longer a reason to write 2021-era code either. The corpus still contains four pages
that render blank for want of those decoders (`bug_jpx.pdf` and the JBIG2 samples).

## Decision

1. **The floor is 1.100.** `rust-version = "1.100"` in every manifest, `msrv = "1.100"`
   in `.clippy.toml` (it *overrides* the manifest for clippy, so the two must move
   together), and CI's `Test (1.100)` job installs it explicitly. 1.100 is the current
   stable, so there is no headroom and that job is the guard against a 1.101-only API.
2. **Every crate is on edition 2024**, and `[workspace] resolver = "3"` — the
   Rust-version-aware resolver the edition makes the default — is stated rather than
   inferred, because `Cargo.lock` is git-ignored and the manifest is the only place
   the reason can live.
3. **The unblocking is recorded, not acted on in this decision.** JPEG 2000 and JBIG2
   move from "blocked" to "scheduled, size decision pending", with the measurements
   below. ICC colour management gains a candidate dependency (`moxcms` 0.9.2: MSRV
   1.89, `BSD-3-Clause OR Apache-2.0`, already on `deny.toml`'s allow-list) and stays
   deferred, because its first question is a fidelity decision, not a dependency one.

## The measurements this rests on

Taken 2026-11-17 by linking both decoders behind temporary features of
`pdf2-render`, reaching them from `Image::from_stream` (so the code is *linked*, not
merely declared), then building the npm package and reverting:

| Bundle | gzip | Δ |
| --- | --- | --- |
| baseline (1.3.0) | 361 056 | — |
| + `hayro-jbig2` 0.4.0, `default-features = false, features = ["std"]` | 423 551 | +62 495 |
| + `hayro-jpeg2000` 0.5.0, same features | 437 108 | +76 052 |
| + both, same features | 498 558 | +137 502 |
| + both, default features (`std`+`image`+`simd`) | 498 939 | +137 883 |

Raw wasm 1 028 054 → 1 639 555 bytes for the "both, std only" case. `image` costs
**381 bytes**, because its `ImageDecoder` implementation is unreachable from a direct
`decode` call and link-time dead-code elimination removes it — so an integration
should take `default-features = false, features = ["std"]`.

**The consequence is a budget decision, not a code one**: the npm bundle budget is
356 KiB and JPX+JBIG2 would need it at **~499 KiB** (a 37 % rise), or a build that
keeps them out of the default bundle (a non-default feature on `pdf2-wasm`, which
means the browser demo does not get them by default).

**Not affected**: the browser (160 KiB) and WASI (187 KiB) budgets. Those modules are
built from `pdf2-wasm-smoke`, whose dependency tree contains no `pdf2-render`
(`cargo tree -p pdf2-wasm-smoke`), so an image decoder cannot reach them at all.

## Consequences

- `cargo install pdf2-cli` now needs **1.100**, and `pdf2`'s consumers do too. That
  is the cost ADR 0004 named, accepted deliberately.
- `.clippy.toml`'s `msrv` is a second copy of the floor for a reason: with it at 1.87
  clippy refused to *suggest* `as_chunks` while the code could not use it. The
  immediate effect of moving it was ten `chunks_exact_to_as_chunks` diagnostics,
  which is how the `as_chunks` sweep became a precondition of the bump.
- Edition 2024's own migration was **empty** (`cargo fix --edition` changed nothing);
  its real effect here was to unlock let-chains, which clippy then asked for at
  thirteen sites. Both are recorded in `CHANGELOG.md` §1.4.0.
- A future bump should start from [`docs/MSRV.md`](../MSRV.md): read the range's
  *Stabilized APIs* and *Language* sections, add one line per release with a verdict,
  and only then change the number.

## What this ADR does not decide

Whether to *spend* 137 KiB of gzip on two decoders, and whether that spending goes
into the default bundle or behind a feature. That is rank 9's next decision and it
needs the budget policy first — `docs/DEFERRED.md` records it as such.
