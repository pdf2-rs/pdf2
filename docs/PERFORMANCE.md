# Performance and memory

Numbers measured by `crates/pdf2-bench` and checked in CI against
[`performance-baseline.json`](performance-baseline.json).

## Method

```sh
cargo run --release -p pdf2-bench -- --check            # the gate CI runs
cargo run --release -p pdf2-bench                       # measure and print
cargo run --release -p pdf2-bench -- --json             # machine-readable
cargo run --release -p pdf2-bench -- --write-baseline docs/performance-baseline.json
```

The binary has no dependencies of its own. It builds one corpus, measures it and
reports five metrics per corpus group plus one process-level number:

| Metric | What it measures | Unit |
| --- | --- | --- |
| `read_mb_s` | open + page walk with content decoding + text extraction, per file size | MB/s (higher better) |
| `pages_s` | pages walked with their content decoded | pages/s (higher better) |
| `text_pages_s` | pages whose text was extracted | pages/s (higher better) |
| `allocations` | allocation calls for one full read pass | count (lower better) |
| `alloc_bytes` | bytes requested for one full read pass | bytes (lower better) |
| `process.peak_rss_kib` | process high-water resident memory | KiB (informational) |

Measurement details, so a number can be reproduced and judged:

- Timings are the **median of 7 samples**; each sample repeats the operation
  enough times to last at least 20 ms, and one warm-up sample is discarded.
  Without that batching, a 500-byte fixture would be a few microseconds and the
  median would track the scheduler rather than the code.
- Allocation numbers come from a counting `GlobalAlloc` installed by the
  benchmark. They are deterministic for a given input: on this machine they are
  bit-identical between runs, which is what makes them a reliable gate.
- Peak RSS uses `VmHWM` on Linux; macOS only exposes the current RSS via
  `ps -o rss=`, so it is recorded but not gated (allocation counts are the
  memory guard).
- The corpus is the committed fixtures (minus the encrypted one) plus files
  generated by this crate's own writer: 1, 100 and 1000 pages, and a 1 MB
  content stream. `PDF2_CORPUS=<dir>` adds real-world PDFs to the report; those
  numbers are never gated because they are not part of the committed baseline.

## The gate

```sh
cargo run --release -p pdf2-bench -- --check
```

- **Deterministic metrics** (`allocations`, `alloc_bytes`) are compared on every
  platform, against whichever baseline entry has them. Growing more than **10%**
  fails the run. This is what CI gates: the runner is Linux and has no timing
  baseline of its own.
- **Timing metrics** are compared against the entry for the current `os-arch`
  only. A platform without an entry has its timings printed and skipped, never
  guessed. The tolerance is the same **10%**; when a metric looks broken the
  benchmark measures once more before failing, so ordinary scheduler noise does
  not trip the gate (the observed cross-process spread is up to ~15% for the
  sub-millisecond groups on the reference machine, so the retry matters).
- `--tolerance <fraction>` overrides the tolerance for an experiment;
  `--runs <n>` changes the sample count.

## Reference numbers

Measured 2026-11-14 with the committed baseline, release profile,
`rustc 1.99.1`, Apple M3 (8 cores), macOS `aarch64`:

| Group | `read_mb_s` | `pages_s` | `text_pages_s` | allocations | alloc bytes |
| --- | --- | --- | --- | --- | --- |
| fixtures (8 files) | 64.4 | 120 259 | 99 338 | 2 044 | 690 519 |
| pages-1 | 55.5 | 63 145 | 58 272 | 236 | 173 340 |
| pages-100 | 31.5 | 422 591 | 292 068 | 9 381 | 1 161 176 |
| pages-1000 | 30.5 | 427 974 | 295 883 | 92 210 | 10 624 288 |
| stream-1mb | 586.5 | 8 347 | 578 | 270 | 14 853 017 |

Peak RSS for the whole run: 18 064 KiB.

What the numbers say:

- Opening is dominated by cross-reference work, so `read_mb_s` grows with page
  count but not with stream size; a 1 MB stream is read at ~580 MB/s because it
  is mostly copied rather than parsed.
- Text extraction costs roughly 0.7× the page walk on generated pages (same
  glyph mapping path, plus the interpreter), and is the slowest metric for the
  1 MB stream because the content stream is one long text run.
- Per-page allocations are flat at ~92 allocations per generated page, which is
  the number to watch when touching the object model.

## Budgets

- Allocation counts and bytes: **no growth** is expected; anything above 10% is
  treated as a regression and should either be fixed or the baseline updated
  deliberately, with the reason in the commit message.
- Throughput: within 10% of the committed baseline for a platform that has one.
- Peak RSS: recorded for observation; the allocation counts are the enforced
  memory metric.

## Updating the baseline

`--write-baseline docs/performance-baseline.json` replaces this platform's entry
and keeps the others, so a Linux number can be added from CI or a Linux machine
without losing the macOS one. Commit the file only when the change is
intentional, and say which metric moved and why in the commit message.

```sh
# on the machine whose measurements should be recorded:
cargo run --release -p pdf2-bench -- --write-baseline docs/performance-baseline.json
```
